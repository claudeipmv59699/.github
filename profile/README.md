<p>项目一多，出口就会乱：A 项目的账号用了 B 项目的 IP，测试号混在主力段里，某条线路超流量了整个组一起断。要避免这种局面，分组得在买线路之前定，而不是出了问题再补。这篇给一份可以照着走的决策清单，四组问题、一张落地表，覆盖按什么维度分组、出口怎么切、权限和账单怎么归、命名怎么定，规模从两三个人到二十几个人都适用。</p>

<h2>一、先回答四个问题，再决定分组粒度</h2>
<p>第一个问题：账号之间是否需要互相看不见。第二个问题：出口出问题时，你能不能接受整组停摆。第三个问题：账单要按人摊还是按项目摊。第四个问题：人员流动的频率高不高。四个答案基本能定下分组粒度——需要互相隔离、不能整组停摆、按项目摊账、人员流动快，就往细里分；反之粗一点更好管。</p>
<p>分组过细的代价是管理成本上升：线路多了要维护台账，权限多了要维护成员表，账单多了要对账。分组过粗的代价是故障扩散：一个出口出事，整组一起受影响。多数团队落在"按项目分、项目内按人授权"这个中间位置。</p>

<h2>二、清单第一组：按账号分还是按团队分</h2>
<p>按账号分适合账号数量少、每个账号都重要的场景，一号一线一条记录，责任到人。按团队分适合账号多、人员多的场景，团队内部共享一段出口，靠权限控制谁能用哪条。两种方式的差别不在技术，在追责路径：按账号分能追到具体账号，按团队分只能追到团队。</p>
<h3>混合模式怎么落地</h3>
<p>实际最常见的是混合：主力账号单独成组，一号一出口；辅助账号按业务线成组，一组共享三到五个出口；测试账号单独一个池子，随便用。这样主力账号的隔离度最高，测试账号的成本最低，中间层按业务线灵活调整。</p>
<h3>一个账号跨项目怎么办</h3>
<p>这种情况要提前定规则：账号归属于主项目，其他项目通过授权借用，借用期间出口不变。最忌讳的是同一个账号在两个项目里各配一个出口，今天用这个明天用那个，出口跳来跳去比一直用一个更糟。</p>

<h2>三、清单第二组：出口资源怎么切，切多细</h2>
<p>切的单位有三个：单 IP、C 段、ASN。单 IP 是最小单位，适合主力账号；C 段适合一组账号，隔离度中等；整段 ASN 级别的划分一般用不上，除非你有几十个账号要分到大块资源里。切的时候注意别把不同项目的账号放进同一个 /24，同段意味着同邻居，项目之间本来该隔离的又贴一起了。</p>

<h3>出口数量怎么估</h3>
<p>一个粗略公式：出口数 = 主力账号数 × 1 + 辅助账号数 ÷ 3 + 1（备用）。十个人的团队、3 个主力号、9 个辅助号，算下来是 3 + 3 + 1 = 7 条线路。备用那条很重要，主力线路维护时能顶上，不至于全员等恢复。</p>

<h2>四、清单第三组：权限、账单和故障归属</h2>
<p>权限按最小可用给：能连线路的人不一定能改配置，能改配置的人不一定能看账单。账单按项目建成本中心，每个项目一个预算上限，超了告警。故障归属要写进值班表：哪条线路归谁盯，出问题先找谁，多久没恢复升级到谁。这三件事在分组的时候一起定，比事后补制度容易得多。</p>
<h3>权限矩阵的最小版本</h3>
<p>三行三列就够：角色（管理员/成员/只读）× 动作（改配置/连线路/看账单）。管理员全开，成员能连线路看自己用量，只读只能看汇总。矩阵贴在团队文档里，新成员入职照着开权限，离职照着关。</p>
<h3>故障归属怎么写</h3>
<p>一条线路至少写两个名字：日常负责人和备份负责人。再写一个判定标准，比如"连续三次拨测失败或延迟超过 800ms 持续十分钟"算故障，触发后自动通知。标准写清楚了，就不用每次争论"这算不算坏了"。</p>

<h2>五、分组落地的最小结构：一张表加一套命名</h2>
<p>落地不需要系统，一张表就够。字段建议八列：项目、账号标识、出口 IP、ASN、绑定时间、负责人、月流量上限、备注。表格放共享文档，改一次记一次，比任何管理后台都直观。</p>

<h3>命名要能一眼看出归属</h3>
<p>比如 proj-a-prod-01-us-lax，看到名字就知道是 A 项目生产环境第一个出口，落地洛杉矶。命名规则定下来之后，线路名、表格行、账单科目三处保持一致，对账的时候不用来回翻译。</p>
<h3>每月复盘看三个数</h3>
<p>出口利用率、单账号平均流量、故障次数。利用率低于三成的线路考虑合并，单账号流量异常高的查是不是被共用，故障次数集中在某条线路上就换服务商。三个数每个月花二十分钟看一遍，比年底一次性整理省力。</p>

<h2>常见问答</h2>
<h3>两三个人的小团队也需要分组吗？</h3>
<p>答：需要，但可以极简。按项目分两个组、留一条备用线路、一张表记清楚就够了，不用上权限矩阵。规模小的时候，规则简单比规则完备更重要。</p>
<h3>不同项目能不能共用一个出口段？</h3>
<p>答：技术上可以，业务上不建议。项目之间本来要隔离，共段等于把隔离度降到同邻居级别，一个项目出问题容易牵连另一个。实在要省成本，至少错开不同 /24。</p>
<h3>分组之后线路不够用，能临时借吗？</h3>
<p>答：可以借，但要记录。借用期间出口不变、借用结束归还，表格里加一行备注写明起止时间。没有记录的借用，三个月后没人说得清哪个号用过哪条线。</p>
<h3>团队成员离职，分组要怎么调？</h3>
<p>答：先收回该成员的子账号权限，再把他负责的线路转给备份负责人，最后更新表格里的负责人字段。三步在一天内完成，避免出现无人认领的线路。</p>

<h2>合规提示</h2>
<p>本文讨论的是团队内部的出口资源管理与权限划分方法，属于常规运维范畴，不涉及规避平台规则。账号数量与用途应符合所使用平台的服务条款。</p>
<p>分组隔离的目的是降低故障影响面与提升可追溯性，不应被理解为可以无限制地批量注册或运营账号。涉及商业用途时，建议保留合同、发票与用量记录。</p>
<p>文中涉及的规模与成本数字为经验区间，仅供参考，实际以团队业务量与服务商报价为准。</p>
